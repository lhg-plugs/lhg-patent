# /lhg-patent:claims —— 权利要求书专项

用户输入在 `$ARGUMENTS` 中：技术特征清单，或已有的 `disclosure.md` / `features.json` 路径。

> ⚠️ **合规声明**：产出为撰写辅助草稿，**须经专利代理人复核后方可用于申请**。

## 流程（加载 claims-draft 全程指导）

### 1. 定保护策略
先和用户定三件事：
- 保护什么：产品？方法？还是两者都要（产品+方法双布局）
- 保护多宽：独立权利要求用上位概括（如"显示装置"而不是"LED 显示屏"），具体实现下沉从属
- 梯度：独立 1~3 项 → 从属若干项，形成"宽→窄" fallback 链

### 2. 写独立权利要求
格式：`一种X，包括A、B，其特征在于，还包括C。`
- 前序部分（"包括A、B"）：写已知技术，承认现有技术
- 特征部分（"其特征在于，还包括C"）：只放**必要技术特征**（features.json 里的）
- 上位概括检查：每个技术特征问一遍"还能不能再上位一层而不丢失发明点"

### 3. 写从属权利要求
- 引用格式："如权利要求1所述的X，其特征在于，……"，只能引用在前编号
- 每项从属增加 1~2 个限定，形成梯度（即使独立被无效，从属还能守住）
- 引用关系画出来检查：不许断裂、不许自引用、不许反向引用

### 4. 跑审计
```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/audit/patent_audit.py --target <工作目录> --format text
```
重点看 PAT-CLM-001/002（引用断裂，blocker）、PAT-CLM-004（保护过窄）、PAT-CLM-005（必要特征缺失）。

## 输出
`claims.txt`（编号连续、引用闭环、每条以句号结尾）+ 末尾合规声明。

## 硬规则
- 独立权利要求超过 3 项 → 提醒用户合并（独立项越多，审查意见越容易各个击破）。
- 从属权利要求引用不存在的编号 → blocker，必须修。
- 不许为了"看起来保护很宽"而写不清楚的特征——不清楚的权利要求等于没写。
