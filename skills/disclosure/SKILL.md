# disclosure：交底书挖掘

> ⚠️ **合规声明（必读）**：本 skill 产出的是**专利撰写辅助草稿**，**不能直接提交专利申请**，
> **必须经专利代理人/代理机构复核**后方可使用；现有技术检索结果不保证查全，
> 新颖性/创造性的最终判断请专利代理人做出。

> 目标：把发明人脑子里的想法，变成一份专利代理人愿意接的交底书。
> 核心纪律：**特征拆得越细，保护写得越宽；三要素说不清，申请基本没戏。**

## 1. 何时使用

- 有个技术想法/产品改进，想申请专利但不知道从何下笔 → 用本 skill 做技术访谈
- 已经写了交底书，评审它够不够"交底" → 按第 5 节清单打分
- 专利代理人退回交底书说"技术特征不清楚" → 按第 3 节重拆

## 2. 输入与输出

**输入**：发明人一句话描述（如"一种带水温显示的智能水杯"）+ 一轮问答。
**输出**：`disclosure.md`（技术特征清单 + 三要素 + 必要技术特征 + 附图说明素材）
与 `features.json`（必要技术特征，供审计脚本检查保护完整性）。

## 3. 分步方法论

### 3.1 第一步：技术访谈（问出真东西）

发明人常说的"我做了一个 X"是不够的，按下面五个问题深挖：

1. **现有技术是什么样的？**（背景技术：别人现在怎么做，有什么毛病）
2. **你的方案和现有技术哪里不一样？**（区别特征，一个一个列）
3. **每个不一样的地方，解决了什么具体问题？**（效果，必须可验证，不能说"更好用"）
4. **有没有替代方案？**（比如显示屏可以用 LED 也可以用电子墨水屏——替代方案是上位概括的素材）
5. **最简方案是什么？**（去掉所有装饰，解决核心问题最少需要哪几个特征——这就是必要技术特征）

**访谈技巧**：发明人说的"创新点"往往是实现细节，真正的发明点藏在"为什么这么做"里。
多问"如果不这么做会怎样"，答案就是技术效果。

### 3.2 第二步：技术特征拆解

把方案拆成**最小技术特征清单**，粒度标准：每个特征一句话能说清，且不能再拆。

示例（智能水杯）：

| 编号 | 技术特征 | 类型 |
|---|---|---|
| F1 | 杯体 | 已知 |
| F2 | 杯盖 | 已知 |
| F3 | 温度显示装置，设置在杯体外壁 | 发明点 |
| F4 | 温度传感器，设置在杯体内壁 | 发明点 |
| F5 | 显示屏为电子墨水屏 | 优选 |

**类型标注**：已知（现有技术里有）/ 发明点（本方案独有的）/ 优选（锦上添花的具体实现）。
"已知"写进前序部分，"发明点"写进特征部分，"优选"下沉到从属权利要求。

### 3.3 第三步：技术问题-手段-效果三要素

每个发明点特征，必须回答三要素（这是专利审查的逻辑主线）：

```
技术问题：现有水杯无法直观显示水温，用户容易被烫伤。
技术手段：在杯体外壁设置温度显示装置，内壁设置温度传感器。
技术效果：用户无需开盖即可获知水温，避免烫伤。
```

**三要素自检**：
- 技术问题必须是**客观存在**的（别编造"现有技术有巨大缺陷"）
- 技术手段必须是**具体可实现**的（"用 AI 优化"不算手段，"用温度传感器+显示屏"才算）
- 技术效果必须**可验证**（能量化的量化，不能的也要能演示）
- 三者之间有因果链：手段→效果→解决问题，链条断了审查员会质疑

### 3.4 第四步：确定必要技术特征

必要技术特征 = 解决核心技术问题**最少需要**的特征集合。

判断方法：**逐个拿掉法**——假设拿掉 F3，核心问题（水温不可视）还能解决吗？
不能 → F3 是必要的；能 → F3 不是必要的，下沉到从属。

必要技术特征写入 `features.json`：

```json
{
  "essential_features": ["温度显示装置", "温度传感器"],
  "note": "解决「水温不可视」问题的最小特征集合"
}
```

审计脚本（PAT-CLM-005）会检查这些特征是否出现在权利要求书中——
必要特征没进独立权利要求，等于白交底。

### 3.5 第五步：准备附图素材

- 画（或描述）至少一张结构示意图，标出每个技术特征的位置
- 每个部件编附图标记（10、20、30…），**全文统一**，附图说明中逐一定义
- 标记规则：同一部件全文同一个号，不同部件不许重号

## 4. 交底书模板

```markdown
# 交底书：<发明名称>

## 一、所属技术领域
<一句话>

## 二、背景技术
<现有技术怎么做，有什么具体缺点>

## 三、发明内容
### 3.1 技术问题
<客观存在的具体问题>
### 3.2 技术方案
<技术特征清单 F1~Fn，标注已知/发明点/优选>
### 3.3 技术效果
<每个发明点特征的效果，可验证>

## 四、必要技术特征
<features.json 内容>

## 五、附图说明
<图1：……；10、杯体；20、杯盖；……>

## 六、替代方案
<每个发明点特征的上位/替代实现，供权利要求上位概括用>

---
合规声明：本稿为 AI 辅助草稿，须经专利代理人复核后方可用于申请。
```

## 5. 反模式（这些交底书会被代理人打回）

1. **特征说不清**："采用先进算法优化体验"——算法是什么、输入输出是什么、优化了哪个指标，一个都说不清。这种描述写不进权利要求。
2. **只有想法没有手段**："我想做一个能自动调温的水杯"——"怎么调"是手段，"想调"是愿望。专利保护的是手段，不是愿望。
3. **效果吹牛**："效率提升 1000%"——没有测试数据的效果别写，写了也得删，还可能影响可信度。
4. **必要特征贪多**：把 10 个特征都标成"必要"——必要特征越多，独立权利要求越窄，越容易被规避。狠心砍到最少。
5. **背景技术贬低现有技术**："现有技术愚蠢地没有想到…"——审查员可能引用你贬低的那篇做对比文件，打脸来得很快。客观描述即可。
6. **附图标记混乱**：正文写（30），附图说明里没有；或者同一个部件两个号。这种低级错误直接拉低代理人对你的信任。

## 6. 自检与反馈

**质检门**（交底书完成前逐项打勾）：

- [ ] 技术特征拆到最小粒度，每个特征一句话说清
- [ ] 每个发明点特征都有问题-手段-效果三要素
- [ ] 必要技术特征用"逐个拿掉法"验证过，写入 features.json
- [ ] 替代方案/上位概括素材已准备（每个发明点至少一个上位词）
- [ ] 附图标记已编号，附图说明可对应
- [ ] 全文无"先进""显著""极大"等无法验证的形容词
- [ ] 末尾有合规声明

**标准冒烟用例**：输入"一种带水温显示的智能水杯"，期望输出 disclosure.md 含 F1~F5 级别的特征清单、
三要素完整、features.json 含"温度显示装置"。

**一键提 issue**：访谈问不出必要技术特征的场景，以 `[disclosure] <一句话场景>` 为标题提交到
https://github.com/lhg-plugs/lhg-patent/issues。
