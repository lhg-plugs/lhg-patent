# claims-draft：权利要求书撰写规范

> ⚠️ **合规声明**：本 skill 产出的是**撰写辅助草稿**，**不能直接提交专利申请**，
> **必须经专利代理人/代理机构复核**后方可使用。

> 目标：写出"引用不断裂、范围有梯度、特征分得清"的权利要求书。
> 核心纪律：**独立权利要求只写必要技术特征；从属权利要求形成宽→窄的 fallback 链。**

## 1. 何时使用

- 交底书已完成，要起草权利要求书 → 用本 skill 走完全流程
- 评审已有的权利要求书：引用关系、保护范围是否合理
- 说明书撰写：本 skill 第 6 节覆盖说明书组织方法

## 2. 输入与输出

**输入**：`disclosure.md`（技术特征清单 + 三要素）+ `features.json`（必要技术特征）。
**输出**：`claims.txt`（编号连续、引用闭环、每条以句号结尾）+ 引用关系说明。

## 3. 分步方法论

### 3.1 第一步：定保护策略（三件事先定）

1. **保护客体**：产品（装置/系统）？方法（工艺/流程）？还是产品+方法双布局？
   双布局保护最全，但撰写工作量翻倍，小白先从产品权利要求起步。
2. **保护宽度目标**：独立权利要求要"宽到竞争对手绕不开，窄到现有技术打不倒"。
   拿捏标准：把每个技术特征问一遍"还能不能再上位一层"。
3. **梯度层数**：独立 1~3 项，从属 5~15 项。独立项太多，审查员容易各个击破。

### 3.2 第二步：写独立权利要求（上位概括的艺术）

标准句式：

```
一种X，包括A、B，其特征在于，还包括C。
```

- **前序部分**（"一种X，包括A、B"）：写**已知技术**——承认现有技术里有的东西，
  别把已知的写进特征部分（那等于把保护范围白送人）。
- **特征部分**（"其特征在于，还包括C"）：只放**必要技术特征**（features.json 里的），
  一个多余的都不要。
- **上位概括**：C 的表述用上位词。交底书写"LED 显示屏"→权利要求写"显示装置"；
  交底书写"螺纹连接"→权利要求写"可拆卸连接"。
  上位的边界：不能上位到"不清楚"（"连接装置"没问题，"固定东西"就是不清楚）。

**上位概括三问**（每个特征过一遍）：
① 去掉这个具体实现，发明点还成立吗？② 上位词本领域技术人员能理解吗？
③ 上位后会不会撞上已知现有技术？三问全"是/能"才上位。

### 3.3 第三步：写从属权利要求（梯度保护）

引用格式：`如权利要求1所述的X，其特征在于，……`

- 每项从属只增加 1~2 个限定（优选特征、具体实现、数值范围）
- 形成梯度：独权（最宽）→ 从属2（+显示屏）→ 从属3（+电子墨水屏），层层 fallback
- 即使独立权利要求被现有技术打掉，从属还有机会守住——**梯度是专利的生命线**

### 3.4 第四步：引用关系检查

- 从属只能引用**在它之前**的编号：权利要求3可以引用1或2，不许引用4，更不许引用自己
- 引用编号必须存在：写完通查一遍，断裂的引用=直接驳回
- 多项引用（"如权利要求1至3任一项所述"）小白慎用：择一关系写错会导致不清楚，先用单项引用

检查方法：跑 `patent_audit.py`，PAT-CLM-001（引用不存在）与 PAT-CLM-002（自引用/反向引用）
是 blocker，必须清零。

### 3.5 第五步：保护范围复核

- **过窄预警**：独立权利要求里"所述""其中"出现 10 次以上，大概率限缩过度——
  把非必要限定下沉到从属（PAT-CLM-004）
- **必要特征检查**：features.json 里的每个必要特征都必须出现在权利要求书中（PAT-CLM-005）
- **不清楚排查**："适当的""较大的"这类相对词不许出现；数值范围写清端点（"10~20"，不写"约15"）

### 3.6 第六步：说明书组织

说明书结构（固定五段）：

1. **技术领域**：一句话，本发明属于什么领域
2. **背景技术**：现有技术怎么做，有什么**具体**缺点（客观描述，不贬低）
3. **发明内容**：技术问题 → 技术方案（对应权利要求）→ 技术效果（三要素照搬交底书）
4. **附图说明**：图1……；10、杯体；20、杯盖——每个标记都要定义
5. **具体实施方式**：至少一个实施例，把权利要求的技术方案"讲一遍怎么做出来"

**说明书铁律**：
- 附图标记全文统一：正文出现（30），附图说明里必须有 30 的定义（PAT-DSC-001）
- 术语全文一致：一套说法用到底，"连接件"和"连接部件"不许并存（PAT-DSC-002）
- 说明书要**支持**权利要求：权利要求里的每个特征，说明书里都要有依据（否则"得不到说明书支持"）

## 4. 完整示例

```
权利要求书

权利要求1
一种智能水杯，包括杯体和杯盖，其特征在于，还包括设置在杯体外壁的温度显示装置。

权利要求2
如权利要求1所述的智能水杯，其特征在于，所述温度显示装置包括显示屏和温度传感器。

权利要求3
如权利要求2所述的智能水杯，其特征在于，所述显示屏为电子墨水屏。
```

读法：权利要求1最宽（任何带温度显示装置的水杯都落入保护）；
权利要求2、3逐层限缩，即使权利要求1被无效，2和3还有机会。

## 5. 反模式

1. **独立权利要求写成说明书**：把 10 个特征全塞进独立权利要求——保护范围窄到竞争对手改一个字就绕开。
2. **特征部分写已知技术**："其特征在于，包括杯体"——杯体是已知的，写进特征部分等于主动限缩。
3. **上位概括上过头**："一种容器，其特征在于，能装东西"——不清楚，直接驳回。上位词必须本领域能理解。
4. **从属引用断裂**：权利要求4引用权利要求9，但全文只有4项——低级但致命，提交前必须跑脚本检查。
5. **说明书不支持权利要求**：权利要求写了"无线充电"，说明书只字未提——审查员一句"得不到说明书支持"就驳回。
6. **功能性限定滥用**："用于显示温度的装置"而不写结构——小白尽量写结构性特征，功能性限定容易被解释得很窄。
7. **数值范围两头不靠**：写"10~20"，实施例只给了 15——端点值最好在实施例里出现过。

## 6. 自检与反馈

**质检门**（权利要求书完成前逐项打勾）：

- [ ] 独立权利要求 ≤3 项，每项只含必要技术特征
- [ ] 前序/特征部分划分正确（"其特征在于"位置对）
- [ ] 每个技术特征都过了"上位概括三问"
- [ ] 从属形成宽→窄梯度，引用关系无断裂/自引用/反向引用（脚本 PAT-CLM-001/002 通过）
- [ ] 保护范围复核通过（PAT-CLM-004/005 无 warning 或已写理由）
- [ ] 每条权利要求独立成段、以句号结尾
- [ ] 说明书五段齐全，附图标记与术语全文一致
- [ ] 末尾有合规声明

**标准冒烟用例**：用 fixtures/bad/claims.txt 跑审计，期望命中 PAT-CLM-001~006；
用 fixtures/good/claims.txt 跑，期望零 blocker。

**一键提 issue**：撰写场景本规范覆盖不了（如方法权利要求、软件专利），以 `[claims] <一句话场景>` 为标题提交到
https://github.com/lhg-plugs/lhg-patent/issues。
